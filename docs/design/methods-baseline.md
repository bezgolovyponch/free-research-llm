## B. The rule for the suppliers pattern (generic, no domain words)
1. BASE (category "fits"): meets every must-have the asker wrote, including anchors the asker named (e.g. "brands similar to A, B, C, D": at least one named anchor present on the item's own page, quote required) — M1 base profile.
2. OPTION (category "trade-off"): an anchor is missing or only of the same class, but every other purpose requirement is fulfilled at a high level (top share of the research's own comparables on the purpose measures: price/value, proven quality, lot size, delivery) — M1 second profile, M5 trade-off shown to the owner.
3. Headline counts BASE only; OPTIONS are listed apart with "lacks: <anchor>; strong on: <measures>".
4. Reuse: the engine already sorts plots into fits / trade-off / weak (row.plan.tier, strategy.mjs) and the cars question asks "20 as fit and up to 80 as a trade off" — generalise that tiering through the decision model; no new layer (F54).

## C. Make it mechanical in the engine
1. src/research/methods.json (universal, no domain words): one entry per method id M1…M5 with source url, verified quote, context, transfer conditions, status verified|supporting.
2. Every decision rule that sorts, vetoes, counts or ranks items carries a method id (constant beside the rule). A test lists the rule ids from decision.mjs, verdict.mjs, checklist.mjs and fails when a rule has no entry, or rests only on a "supporting" entry.
3. scripts/quality.mjs gains a "methods" check: every entry with status verified must have its quote found in a stored snapshot of the source text (tests/fixtures/methods/<id>.txt, fetched once and committed), so a citation cannot drift or be invented.
4. Owner view: the result page shows each category's profile and the method id it rests on.
5. Zero-loss rules apply (same 8 conditions): BASE must not lose an item the old verdict confirmed correctly; OPTIONS are additions, never moved into the headline.
