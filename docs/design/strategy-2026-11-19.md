# Engine strategy: precision, token spend, self-improvement, gates, zero loss (2026-11-19)

Owner's priorities, in order: (1) precision of the research, (2) LLM token spend, (3) a bulletproof, self-improving engine logic, (4) mikoshi-construct application with mechanical gates that compare results, (5) no loss of current value.

Every method below was checked on its paper (abstract or full text). "Have" is what the engine does on main b2967d3, read from the code. Numbers from 19 Nov: 1189 model calls, 31% failed (groq per-minute quota 180, payload too large 21, gemini 503 14, pollinations 402 13); 2.43M tokens: research 40%, checklist judge 32%, improve loop 8%.

## 1. Foundation: the LLM proposes, code verifies (governs every row below)
- Kambhampati et al., LLM-Modulo, ICML 2024 (arXiv 2402.01817): "auto-regressive LLMs cannot, by themselves, do planning or self-verification"; use them as "universal approximate knowledge sources" with external verifiers.
- Zave & Jackson, TOSEM 1997: K, S ⊢ R. Requirements are about the world; domain knowledge K plus the specification S must imply them.
- Rule for FRL: every model output (decomposition, checklist, judgement, memo) is a proposal; it counts only after a code check (measure, quote on the page, trace to a requirement, independent second family). This is the existing direction (mechanical gates); the gaps below are where it is not yet applied.

## 3. Order (no loss, no conflict with the other session)
Phase A, now, files the other session does not touch:
1. methods baseline: add the rows above with their quotes (docs).
2. waste meter: scripts over data/logs/model-calls.jsonl, per purpose and research; quality warns above 15% failed calls.
3. reference gate: wire scripts/measure.mjs paired comparison against the frozen snapshot ~/frl-wt/lead/snapshot-2026-11-19 into npm run quality (reports first, fails once the baseline is recorded).
4. router waste: too-large request → larger context; no paying provider on the free route. Only after confirming the other session's Sonnet-in-votes work does not touch the router.

Phase B, after the other session's stack merges, one PR each, the 8 zero-loss conditions on the snapshot plus the reference gate:
1. C13 knowledge nodes (kind gate only on item-finding nodes).
2. C15 place roles.
3. Request model (decomposition) extending the concept frame.
4. Read once everywhere.
5. Code first, judge survivors.
6. Adaptive second opinions; small batches for hard checks.
7. Loop target and playbook lessons (GEPA, ACE).
8. Plan reuse per kind.
9. Results view on the single headline.
B4-B8 must show fewer calls on the waste meter, or they do not merge.
